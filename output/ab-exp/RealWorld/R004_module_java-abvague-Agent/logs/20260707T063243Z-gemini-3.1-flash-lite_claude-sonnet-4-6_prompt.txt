=== Turn 1 ===
The `Animal` class is becoming bloated with excessive responsibility regarding its lifecycle, movement, food-finding, and disease management. Please extract the logic related to disease management into a separate component to reduce the complexity of the `Animal` class.

=== Turn 2 ===
The `Simulator` class is currently handling too many responsibilities, including managing the simulation clock, weather, population counts, GUI listeners, and the main simulation loop. Please extract the logic related to the simulation lifecycle and actor management into a separate `SimulationEngine` class to improve modularity and clean up the `Simulator` class.

=== Turn 3 ===
The `Field` class is currently handling both raw grid data management and complex query operations like `getRandomFreePatches` and `getFreePatches`. Please extract the spatial query and analysis logic from `Field` into a dedicated `FieldAnalyzer` component to improve the `Field` class's focus as a container.

=== Turn 4 ===
The `SimulationEngine` currently contains a hardcoded population logic within its `populate()` method, which makes it difficult to extend the simulation with new species or change the initialization strategy without modifying the core engine. Please implement the Strategy pattern by extracting the population logic into a separate `PopulationStrategy` interface and provide a default implementation to keep the engine configuration decoupled from the population generation mechanism.

=== Turn 5 ===
The `DiseaseManager` currently couples disease logic directly to the `Animal` class, creating a tight dependency that makes it difficult to change how diseases are managed or to apply them to other `Organism` subclasses in the future. Please introduce a `DiseaseAware` interface and refactor the `DiseaseManager` to operate on that interface, ensuring that the logic is decoupled from specific `Animal` implementations.

=== Turn 6 ===
The `SimulatorView` class is currently doing too much by handling GUI construction, event listener management, statistical display, and low-level rendering through its nested `FieldView` class. Please extract the rendering logic into a standalone `FieldRenderer` component and move the statistics display and GUI event handling into a more modular structure, ensuring the `SimulatorView` only acts as a high-level orchestrator for these UI components.

=== Turn 7 ===
The `FieldStats` class is currently doing two things: it maintains the counts for simulation participants and it contains business logic to determine the viability of the simulation (e.g., checking if multiple species are alive). Please extract the viability logic into a `SimulationViabilityEvaluator` component to separate the concerns of statistical collection from the simulation rules.

=== Turn 8 ===
The `SimulationEngine` currently manages the time and weather logic directly within its `step()` method. Please extract the `Time` and `Weather` management into a dedicated `EnvironmentManager` component to simplify the engine's core loop and encapsulate environment state transitions.

=== Turn 9 ===
The `Animal` and `Plant` classes currently use inheritance to share characteristics, but both inherit from `Organism` and implement `Actor`. As new types of entities are introduced, this deep inheritance hierarchy is becoming rigid and difficult to manage. Please refactor the codebase to favor composition over inheritance by creating a component-based model where behaviors like `Aging`, `Hunger`, and `Growth` are modular components that can be added to any `Actor` as needed.

=== Turn 10 ===
The current simulation logic in `SimulationEngine` involves manual checks for whether an organism is a `Plant` or an `Animal` to decide if it should grow or age/starve. This pattern is fragile and violates the Open/Closed Principle. Please refactor the actor loop by defining a `Tickable` interface (or using an existing one) to provide a standard `tick()` method for all lifecycle components, allowing the `SimulationEngine` to simply invoke a collection of `Tickable` components for each actor without knowing their specific types.
